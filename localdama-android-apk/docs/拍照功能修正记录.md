# 拍照功能修正记录

## 概述

对身份证拍照 → OCR 识别 → 结果展示的全链路进行了问题排查与修正，涉及 Bug 修复、业务文案重构、内存泄漏治理三个方面。以下是各项改动的根因分析与修正方案。

---

## 一、拍照后无响应（致命 Bug）

### 根因

`IdCardCameraScreen.kt` 中 `ImageCapture` 使用了 `CAPTURE_MODE_MINIMIZE_LATENCY` 模式。在 CameraX 1.4.1 中，该模式下 `ImageProxy` 的输出格式为 **YUV_420_888**（原始 YUV 数据），而非 JPEG。

原代码直接从 `image.planes[0].buffer` 取出 Y 平面原始字节，传给 `BitmapFactory.decodeByteArray` 解码：

```kotlin
// 修复前
val buffer = image.planes[0].buffer
val bytes = ByteArray(buffer.remaining())
buffer.get(bytes)
val bmp = BitmapFactory.decodeByteArray(bytes, 0, bytes.size) // YUV 数据无法解码，始终返回 null
image.close()

if (bmp == null) {
    isCapturing = false
    Log.e(TAG, "拍照解码失败")  // 每次都走这里，但用户无感知
    return
}
```

`BitmapFactory.decodeByteArray` 只能处理 JPEG/PNG/WebP 等压缩格式，对 YUV 原始数据返回 null，后续 OCR 和页面跳转不会执行，表现为"点击拍照无响应"。

### 修正方案

使用 CameraX 提供的 `ImageProxy.toBitmap()` 方法（1.3.0+ 可用），内部自动处理 YUV_420_888 与 JPEG 两种格式的转换：

```kotlin
// 修复后
val bmp = image.toBitmap()  // 自动处理格式转换
image.close()
```

**影响文件：** `app/src/main/java/com/yyt/dama/feature/idcard/IdCardCameraScreen.kt`

## 二、相机反复重绑定（潜在隐患）

### 根因

`IdCardCameraScreen.kt` 中 `AndroidView` 的相机绑定守卫变量 `bindingStarted` 是 Composable 函数内的局部变量，每次重组都重置为 `false`：

```kotlin
// 修复前
var bindingStarted = false  // 每次 recomposition 重置
AndroidView(
    factory = { ... },
    update = { previewView ->
        if (!bindingStarted) {
            bindingStarted = true
            // provider.unbindAll() + bindToLifecycle() ...
        }
    }
)
```

`AndroidView` 的 `update` lambda 在每次重组时都是新对象，会被重新执行，导致相机被反复 `unbindAll()` + `bindToLifecycle()`，处于不稳定状态。

### 修正方案

使用 `remember { mutableStateOf() }` 持久化绑定标记，确保相机绑定只执行一次：

```kotlin
// 修复后
val bindingStarted = remember { mutableStateOf(false) }
AndroidView(
    factory = { ... },
    update = { previewView ->
        if (!bindingStarted.value) {
            bindingStarted.value = true
            // 绑定相机...
        }
        applyCameraSettings?.invoke(flashOn, zoomRatio)
    }
)
```

**影响文件：** `app/src/main/java/com/yyt/dama/feature/idcard/IdCardCameraScreen.kt`

## 三、错误场景缺少用户反馈

```kotlin
} catch (e: Exception) {

```

## 四、结果页提示文案按业务来源区分

### 根因

结果页的"未检测到文本区域"提示和弹窗文案是固定写死的，无法区分不同业务场景（身份证打码、敏感信息打码、OCR 测试）。弹窗标题和确认按钮也是硬编码的中文字符串。

### 修正方案

**1. 新建 `DetectionSource` 枚举**（`navigation/DetectionSource.kt`），每个枚举值关联两组 `@StringRes` 资源 ID：

```kotlin
enum class DetectionSource(
    @StringRes val noRegionsTextRes: Int,
    @StringRes val dialogHintRes: Int
) {
    ID_CARD(R.string.result_no_regions_id_card, R.string.result_dialog_hint_id_card),
    SENSITIVE(R.string.result_no_regions_sensitive, R.string.result_dialog_hint_sensitive),
    OCR_TEST(R.string.result_no_regions_ocr_test, R.string.result_dialog_hint_ocr_test),
    DEFAULT(R.string.result_no_regions_default, R.string.result_dialog_hint_default)
}
```

**2. 在 `strings.xml` 中按业务来源定义文案**，消除硬编码：

| 资源 Key | 值 |
|---|---|
| `result_no_regions_id_card` | 未识别到身份证信息 |
| `result_no_regions_sensitive` | 未识别到敏感信息 |
| `result_no_regions_ocr_test` | 未识别到文本区域 |
| `result_no_regions_default` | 未检测到文本区域 |
| `result_dialog_hint_id_card` | 身份证识别失败，确保信息清晰、边框完整 |
| `result_dialog_hint_sensitive` | 敏感信息识别失败，请确保内容清晰可见 |
| `result_dialog_hint_ocr_test` | 文本识别失败，请更换清晰的测试图片 |
| `result_dialog_hint_default` | 识别失败，请确保内容清晰可见 |
| `result_dialog_title` | 识别提示 |
| `result_dialog_confirm` | 确定 |

**3. `ResultScreen` 新增 `source: DetectionSource` 参数**，动态选择文案：

```kotlin
Text(text = stringResource(source.noRegionsTextRes), ...)
Text(text = stringResource(source.dialogHintRes), ...)
```

**4. `DamaNavGraph` 新增 `sharedSource` 共享状态**，各跳转入口设置对应来源后传递给 `ResultScreen`：

| 跳转入口 | 设置值 |
|---|---|
| 身份证拍照 (`IdCardCamera`) | `DetectionSource.ID_CARD` |
| 身份证编辑 (`IdCardEdit`) | `DetectionSource.ID_CARD` |
| OCR 测试 (`HomeScreen`) | `DetectionSource.OCR_TEST` |

后续新增业务场景只需：在枚举加一个条目、在 `strings.xml` 加两条字符串、在跳转前设置来源。

**影响文件：** `navigation/DetectionSource.kt`（新增）、`res/values/strings.xml`、`feature/result/ResultScreen.kt`、`navigation/DamaNavGraph.kt`

## 五、内存泄漏治理（5 处）

### 5.1 检测失败时拍照 Bitmap 未回收

**根因：** `runFullImageDetection` 抛异常时，catch 块中没有 `bmp.recycle()`，一张全分辨率相机照片（5-20MB）泄漏。

**修正：** catch 块中增加 `bmp.recycle()`：

```kotlin
} catch (e: Exception) {
    Log.e(TAG, "检测失败", e)
    bmp.recycle()  // 新增
    isProcessing = false
    Toast.makeText(context, "识别失败，请重试", Toast.LENGTH_SHORT).show()
}
```

**影响文件：** `IdCardCameraScreen.kt`

---

### 5.2 ONNX SessionOptions 原生句柄泄漏

**根因：** `OcrDetector.init` 中 `SessionOptions` 创建后未调用 `close()`，每次构造 `OcrDetector` 都泄漏一个原生句柄。

**修正：** 使用 Kotlin `use {}` 自动管理生命周期：

```kotlin
// 修复后
init {
    val modelBytes = context.assets.open("models/Paddle/det_v5.onnx").readBytes()
    OrtSession.SessionOptions().use { options ->
        options.setIntraOpNumThreads(4)
        options.setOptimizationLevel(OrtSession.SessionOptions.OptLevel.ALL_OPT)
        session = env.createSession(modelBytes, options)
    } // options 自动 close
}
```

**影响文件：** `engine/OcrDetector.kt`

---

### 5.3 重新选图时旧 Bitmap 未回收

**根因：** `IdCardEditScreen` 的 PhotoPicker 回调中直接赋值新 Bitmap，旧 `selectedBitmap` 没有 `recycle()`。用户反复选图时每次泄漏一张大图。

**修正：** 先保存旧引用，赋新值后再回收旧图：

```kotlin
// 修复后
val old = selectedBitmap
selectedBitmap = bmp
old?.recycle()
```

**影响文件：** `feature/idcard/IdCardEditScreen.kt`

---

### 5.4 快速切换打码风格时 Bitmap double-recycle 竞态

**根因：** `ResultScreen` 的 `LaunchedEffect(currentStyle)` 中，`old = displayBitmap` 在 effect 开头捕获。如果用户快速连续切换风格，两次 effect 可能捕获同一个 Bitmap 引用并各 recycle 一次，导致 `IllegalStateException`。

**修正：** 引入 `pendingRecycle` 暂存机制，延迟一帧回收：

```kotlin
var pendingRecycle by remember { mutableStateOf<Bitmap?>(null) }

LaunchedEffect(currentStyle) {
    if (hasRegions) {
        pendingRecycle?.recycle()       // 回收上轮暂存的（已不在渲染管线中）
        val newBmp = MosaicEngine.applyMosaic(originalBitmap, detectedRegions, currentStyle)
        pendingRecycle = displayBitmap  // 当前 bitmap 暂存，而非立即 recycle
        displayBitmap = newBmp
    }
}

DisposableEffect(Unit) {
    onDispose {
        displayBitmap.recycle()
        pendingRecycle?.recycle()       // 退出时一并回收暂存的
    }
}
```

**原理：** 每次风格切换只回收"上上轮"的 Bitmap（已确认不在渲染管线中），当前正在渲染的 Bitmap 存入暂存区，保证 `pendingRecycle` 和 `displayBitmap` 始终指向不同对象，杜绝 double-recycle。

**影响文件：** `feature/result/ResultScreen.kt`

---

### 5.4 sharedOriginalBitmap 依赖 GC 延迟回收

**根因：** `DamaNavGraph` 退出结果页时只将 `sharedOriginalBitmap` 置 null，5-20MB 的相机大图完全依赖 GC 延迟回收，在内存紧张设备上增加 OOM 压力。但不能立即 `recycle()`，因为退出动画期间 Compose 可能仍在渲染。

**修正：** 通过 `Handler.postDelayed(500ms)` 延迟回收，退出动画完成后及时释放 native 像素：

```kotlin
DisposableEffect(Unit) {
    onDispose {
        val bitmapToRecycle = sharedOriginalBitmap
        sharedOriginalBitmap = null
        sharedRegions = emptyList()
        sharedSource = DetectionSource.DEFAULT
        if (bitmapToRecycle != null) {
            Handler(Looper.getMainLooper()).postDelayed({
                if (!bitmapToRecycle.isRecycled) {
                    bitmapToRecycle.recycle()
                }
            }, 500)
        }
    }
}
```

500ms 足以覆盖退出动画时长，`isRecycled` 防护避免重复回收。

**影响文件：** `navigation/DamaNavGraph.kt`

## 八、拍照全图 OCR → 裁剪区域 OCR（核心重构）

### 根因

拍照后直接调用 `runFullImageDetection` 对整张全分辨率照片做 OCR，仅靠模板区域过滤（`overlapRatio > 0.15f`）来筛选与模板重叠的文本框，背景中的文字可能侥幸通过过滤，导致识别范围不精确。

### 修正方案

参考 CameraCrop 项目的「两步裁剪法」：

1. **Step 0（方向对齐）**：`rotateToMatchScreen()` — 相机传感器输出横向照片（4000×3000），手机竖屏握持（viewRatio=0.45），裁剪前先旋转 90° 对齐。
2. **Step 1（等比例裁剪）**：`cropToPreviewRatio()` — 裁剪为与 PreviewView 等宽高比（中心对齐），消除传感器/屏幕比例差异。
3. **Step 2（取景框裁剪）**：`cropToOverlay()` — 按取景框百分比坐标裁出卡片区域。
4. **OCR**：对裁剪后的卡片区域调用 `runTemplateDetection`，仅卡片内文字被检测。

**影响文件：**
- `app/src/main/java/com/yyt/dama/util/CropUtils.kt`（新增）
- `app/src/main/java/com/yyt/dama/feature/idcard/IdCardCameraScreen.kt`

## 十三、反面拍照误用正面模板（区域筛选错位）

### 根因

`IdCardTemplate.kt` 本身定义正确——正面（`landscapeTemplate` / `portraitTemplate`）与反面（`landscapeBackTemplate` / `portraitBackTemplate`）是四套独立模板，`templateFor(orientation, side)` 也能根据 `side` 正确返回反面模板。

问题出在调用方：相机拍摄反面时，OCR 区域筛选用的还是正面模板。

`IdCardCameraScreen.kt` 的 `captureAndDetect()` 中有一行被注释掉的代码：

```kotlin
//            val capturedSide = currentSide  // 捕获当前面
val capturedOverlay = overlayPercentRect  // 捕获当前取景框位置
```

原本设计要在拍照瞬间捕获 `currentSide`（用户当前选的正/反面），但被注释掉后 `currentSide` 没有传递下去。随后在预览确认回调里：

```kotlin
val regions = withContext(Dispatchers.IO) {
    runTemplateDetection(context, bmp)   // ← 没传 side，默认 FRONT
}
```

而 `runTemplateDetection` 的签名根本没有 `side` 参数，内部 `templateFor(orientation)` 永远用默认的 `FRONT`：

```kotlin
fun runTemplateDetection(
    context: Context,
    original: Bitmap,
    orientation: CardOrientation = CardOrientation.LANDSCAPE,
    searchPadding: Float = 0.4f
): List<Rect> {
    ...
    val textFields = templateFor(orientation).filter { !it.isDashed }  // ← side 默认 FRONT
```

**影响：** 无论 UI 上选的是「正面」还是「反面」标签，拍完照后 OCR 区域筛选用的都是正面模板（姓名/性别/出生/住址/号码），而不是反面模板（国徽/签发机关/有效期限）。反面该打码的「签发机关」「有效期限」会漏掉，不需要打码的位置可能被误框。

同样问题的地方：

| 文件 | 位置 | 问题 |
|---|---|---|
| `DetectionEngine.kt` L148 | `runTemplateDetection` | 函数签名缺 `side` 参数，内部 `templateFor(orientation)` 用默认 `FRONT` |
| `DetectionEngine.kt` L21 | `runDetection` | 同样没有 `side` 参数，L46 `templateFor(orientation)` 用默认 `FRONT` |
| `IdCardCameraScreen.kt` L307 | 拍照确认回调 | 调用 `runTemplateDetection(context, bmp)` 没传 `side`，且 `capturedSide` 被注释 |
| `IdCardEditScreen.kt` L219 | `templateFor(orientation)` | 编辑页也只按方向取模板，没区分正反面 |
| `IdCardEditScreen.kt` L413 | `runDetection(...)` | 没传 `side` |

唯一正确的路径是 `runDualSideDetection`（`DetectionEngine.kt` L102-130），它显式对正面传 `CardSide.FRONT`、对反面传 `CardSide.BACK`——但这是「双面拼接」专用，相机单张拍摄流程并没有走它。

### 修正方案（最小修复）

本次只修复让反面拍照能正确筛模板的三处，不涉及编辑页 UI 改动。

**1. `DetectionEngine.runDetection` 加 `side` 参数：**

```kotlin
fun runDetection(
    context: Context,
    original: Bitmap,
    cardOffsetY: Float,
    screenW: Float,
    cardH: Float,
    orientation: CardOrientation = CardOrientation.LANDSCAPE,
    side: CardSide = CardSide.FRONT   // 新增
): Pair<Bitmap, List<Rect>> {
    ...
    // 模板过滤（排除照片/国徽区域，这些区域不需要 OCR 文本匹配）
    val regionRects = templateFor(orientation, side).filter { !it.isDashed }.map { it.toRect(imgW, cropH) }
```

## 十四、正面模板坐标优化（基于 OCR 检测反馈）

### 根因

正面模板（`landscapeTemplate`）的初始坐标基于估算值，与身份证实际文字行位置有偏差：
- 姓名、性别/民族、出生日期的 y 坐标偏高或偏低
- 出生日期模板落在两行文字之间的空白区，OCR 漏检
- 住址区域包含大量空白行，搜索区扩展后覆盖相邻字段导致重复检测
- 搜索区向左侧扩展导致超出身份证边缘

### 修正方案

通过 `TemplateDebugVisualizer` 生成四色对比图（绿=模板字段、黄=搜索区、红=OCR 原始框、蓝=最终打码区域），根据 OCR 实际检测框的像素坐标反推出精确的模板百分比坐标。

**1. 模板坐标优化（`IdCardTemplate.kt`）：**

| 字段 | 旧值 (y, h) | 新值 (y, h) | 原因 |
|------|-----------|-----------|------|
| 姓名 | 0.07, 0.10 | 0.13, 0.06 | OCR 框 y=89~118 |
| 性别/民族 | 0.20, 0.08 | 0.26, 0.05 | OCR 框 y=173~194 |
| 出生日期 | 0.31, 0.08 | 0.38, 0.05 | OCR 框 y=250~270 |
| 住址 | 0.44, 0.28 | 0.51, 0.22 | OCR 框 y=333~404，上下冗余 |
| 身份证号 | 0.77, 0.12 | 0.83, 0.05 | OCR 框 y=536~555 |

**2. 搜索区左边界不再扩展（`DetectionEngine.expandRegion`）：**

搜索区仅向**上、右、下**三个方向扩展 20%，左边界保持与模板区域一致，避免超出身份证左侧边缘。

**3. 打码区域按行统一高度扩展（`DetectionEngine.expandOcrBoxes`）：**

- 同一行内的 OCR 框按垂直重叠分组
- 每行取所有框的**最大高度**作为统一扩展基准（而非各自独立扩展）
- 水平扩展改为固定值 `imgW * 2%`（而非按框宽度比例），保证所有行左对齐一致
- 解决数字框比中文框矮导致的数字打码不完整问题

**4. OCR 漏检兜底（`DetectionEngine.runTemplateDetection`）：**

当模板搜索区内 OCR 检测到 0 个框时，用模板区域本身外扩 15% 作为兜底打码区域，防止文字行漏检导致不打码。

**5. 调试可视化工具（`TemplateDebugVisualizer.kt` 新增）：**

- 长按主页「OCR 测试」卡片触发调试模式
- 生成四色对比图：绿=模板、黄=搜索区(20%扩展)、红=OCR 原始框、蓝=最终打码区域
- 输出每个字段的 OCR 框坐标、合并边界百分比，供定位偏差

### 最终打码流程

```
模板区域(绿) + 20%上/右/下扩展 = 搜索区(黄)
  → OCR 检测 → 原始框(红)
  → 按行分组, 统一行高 × 20% + 固定水平 2% → 打码区(蓝)
  → 若 0 框 → 模板区域 15% 兜底
```
